# Philosophies of resource metadata

How a system decides where facts about a resource live is a choice among a few stances, and each one buys something and costs something. Naming the stance up front makes the cost visible before it is paid.

All of these assume metadata sits on hand-written code and describes it. A system where an external spec is the contract and the code is generated from it is a different architecture, not another stance on the same page (see [spec-or-metadata](spec-or-metadata.md)).

| Stance | Where the facts live | Example | Cost |
|---|---|---|---|
| Metadata is a declarative language | A small language beside the code: comment markers or inline tags | [controller-gen](../case-studies/controller-gen.md) reads `//+kubebuilder:` markers on Go structs and emits CRD YAML | The marker layer is stringly. A misspelled `//+kubebuilder:validation:enum` is silently ignored, and a common validation shape stayed unexpressible for six years. You owe a separate linter the format won't give you. |
| Metadata is ordinary Go data | Typed Go values, held as the single authority | [ent](../case-studies/ent.md) schemas are Go structs returning typed field and edge declarations; a generator emits a typed client | A large generated surface. The code you read while debugging is generated, and every schema change means regenerate and rebuild before it takes effect. |
| Code is the metadata | What the code already is or does; authored metadata covers only the residue | [upjet](../case-studies/upjet.md) derives schema, controller logic, and sensitive-field handling from the existing Terraform schema and asks only for what it can't infer | You need an existing authority to read from. References to fields stay stringly and unchecked unless you also generate field constants, and migration-era facts leak back into hand-authored config. |
| Wiring is explicit composition | Nowhere declarative; resources are assembled in ordinary Go | A [controller-runtime](../case-studies/controller-runtime.md) operator builds a Manager in `main.go` and registers each controller by hand | No central list enumerates what exists, so an omitted registration fails silently, and every controller inherits the shared machinery's defaults (cached reads) and its version churn. |
| Metadata is consumed, not compiled | Typed declarations read at runtime by one generic implementation; little or nothing generated per resource | [database/sql](../case-studies/database-sql.md) registers a driver value against a one-method interface and runs every database through the same runtime | The shared runtime concentrates behavior away from the resource, so "why did this one do that?" means reading shared code. A bug's blast radius is every consumer, and the registry is mutable global state that fails at runtime, not compile time. |

The third stance is worth separating from the second. Both end in Go, but one authors facts as data and the other reads them out of code that already exists. Deriving before authoring is its own idea ([derive-before-authoring](derive-before-authoring.md)); the catch is that it only works where there's code to read, and it tends to recover an implementation detail (a Go type) when what you wanted was the resource fact behind it ([spec-or-metadata](spec-or-metadata.md)).

The last stance carries a tradeoff that doesn't resolve cleanly. Generated per-resource code is inspectable: you can read, diff, and debug the exact lines for one resource, and a bug touches that resource only. A shared runtime is the opposite on both counts, easier to change in one place and harder to explain because the behavior isn't where the resource is. I don't think either dominates. It's a default with a stated cost, not a replacement.

One assumption hides under all of this: that two subsystems with different programming models must share one stance. They don't have to. If two plugin frameworks, or two halves of a system, already differ in how they're written, nothing requires them to author metadata the same way. Treating uniformity as a requirement rather than a convenience rules out splitting by subsystem for no reason anyone wrote down. Whether to split is a judgment; requiring sameness is the part to question.
